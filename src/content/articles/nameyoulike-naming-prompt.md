让 AI 起一批名字几乎总能拿到结果，难的是判断哪个能用。模型不会顺手告诉你某个词在 npm 上已经有人占了，也不会承认这批候选里有四个是同一个动作词换了个修饰。NameYouLike 的 `prompt.txt` 把起名排成一条链：先查撞名，按配额取材，逐名按固定判据评审，不够就补，最后跑完域名、npm、GitHub、商标核验才交付。每一步都有可判定的出口，评审才不至于落到一句“我觉得还行”。

## 输入缺项先问，输出固定字段

输入列成清单：产品描述、名字用在哪、已知同类产品、最讨厌的名字类型、已否决的候选、名字数量。产品描述缺失或含糊时，一次把问题列完，等回答再起名；其余项可填“无”，数量留空默认 8 个。

输出先给人读的列表，再给程序读的 JSON，两者内容一致。列表一行一个名字，写清包名、读音、域名及状态、npm 与 GitHub 与商标的核验结果、一句话由来。JSON 的 `kept` 按实际条数填，`rejected` 逐条列出淘汰的名字、违反的规则和下一步取材方向。字段固定下来，理由才挂得住。

## 起名之前先查撞名

排查放在生成之前，提示词写的是“不查不起名”。GitHub 搜 `<候选名>+in:name` 看仓库数与 star，查 `registry.npmjs.org` 的返回码，再用 web_search 搜一圈。同名仓库数只作参考，star 高且仍在维护的才算真撞名。同类产品单独查一遍，用产品描述里的关键词加“工具”“项目”“开源”去搜，输入里没填就主动补上。结论写进 `analysis.factsKnown`，取材和评审都从这里避让。先知道哪些词被占了，方向一开始就绕开，不至于整批起完再推倒。

## 配额和家族计数

动手前先排结构计划：纯实词最多 2 个，造词或短写 2 到 3 个，带前缀装饰的 2 到 4 个。这几个数是上限，某一类配不出合格名字就整条放弃，在 `factsGaps` 里写明没配出来，不为凑类型硬造。纯实词最容易撞名也最容易没好域名，所以造词和前缀名优先。

家族计数比配额更细。一个词出现在超过 3 个候选里就算扎堆，只留产品关联最强的那个。四个“修饰词 + 同一个动作词”的名字，像 ShareParse、PostParse、VideoParse、ClipResolve，修饰词各不相同仍然算一家，要换掉其中几个动作词。同一主体拆出的变体，加后缀、换同义词、只差一个前缀，只算一个名字，不单独占名额。这条挡的是“看着有八个，其实是一个”。

## 评审判据的三个方面

每个候选按产品关联、词面、联想的顺序过一遍。保留要给证据，淘汰要点名规则和补充方向。

产品关联看 `productFact` 有没有引用输入里的原词，理由要落到具体动作、对象或边界上。“提升效率”“更简单”“有科技感”不算证据。语义还得跟产品边界对上：fetch、pull、download、stream 会先被读成服务端取回内容，用在“只解析不存储、零带宽”的产品上就不成立；feed 像信息流，fold、funnel、junction 像汇聚，peek、preview 像查看内容，对不上就是不对。名字还要提示业务，取了龙头、火石这类器物却没有动作或领域线索的，同样不成立。

词面上，一个具体词、两个真实词组合、一个读得通的造词，至少要有一个具体物件、具体动作或清楚的方向。两个通用褒义词拼在一起（Bridgescape、Flybridge），靠外语释义才成立的名字（Ikena），parser、fetcher、kit、hub 这类通用技术词单独当名字，都不合格。包名用小写字母、数字和连字符，主体不超过 15 个字符，展示名有两个以上词就拆开加连字符，socket set 写 socket-set，NineParse 写 nine-parse。

联想按来源分档。真实词列三条不同联想，物件、场景、日常用法各一条；造词和前缀名列两条可感知的联想，读音节奏带来的感觉，以及可能指向的方向。不编词源故事。主名 2 到 3 个音节最合适，5 个音节以上先换短。

## 补齐不许降标准

过审不够就换来源或角度补新名，补进来的重新评审。已保留、已否决、本轮淘汰的名字都不再生成，只差字母、后缀、同义词或同一主体变体也算重复。名额已满但发现扎堆，照样换掉再补。降标准、加通用后缀凑数、把补齐的活交回用户，这三件都不许。交付时记录补齐轮数、补上几个、逐名淘汰理由。

短交只在事实不足或方向耗尽时允许，在 `factsGaps` 写清缺什么、为什么补不出、还需要用户答什么。

## 域名核验链：DoH、RDAP、WHOIS

域名状态定成六选一：可注册、已注册、溢价、保留、挂牌出售、未确认。查不清就写未确认，不写“可能可用”，也不把 429、超时、空响应当可注册。

`scripts/domain-check-fast.py` 把查询分三段。DoH 查 NS 记录，有记录说明域名已经委派，直接判已注册，这一趟不问注册局也没有限流；NXDOMAIN 只说明这个名字在区里没有委派，已注册但没配 NS 的域名也长这样，必须回 RDAP 确认。权威 RDAP 每个后缀只认自己那份：com、net 用 Verisign，io、ai、sh 用 Identity Digital，dev、app 用 Google Registry，xyz 用 CentralNic。聚合站实测时好时坏，会 403 或限流，不拿它的结果下结论。404 是没有记录，200 是有记录，响应带 reserved 写保留，带 premium 写溢价，否则写已注册，创建与到期时间、注册商从 events 和 entities 里读。

限流按后缀分开。dev、app 最严，11 月 4 日实测并发 6 个全部正常，并发 12 个里 8 个 429，并发 24 个全部 429，所以这两个后缀串行查、间隔 400 毫秒，其他后缀并发 2。碰到 429 按 0.8 秒、2 秒、4 秒退避，三次仍是 429 就写未确认。

WHOIS 只在 RDAP 没结论时兜底，且只对 com、net、io、ai、me、sh、so 有效。dev、app 的 WHOIS 对已注册和不存在的域名都回空串，实测如此，这两个后缀不回退。本机 DNS 可能被代理劫持编造假地址，解析结果不能单独下结论。

```bash
python3 scripts/domain-check-fast.py --variants link-parse,direct-fetch --json out.json
```

## 域名空着，npm、GitHub、商标也要空着

域名可注册只是一项。npm 查 `registry.npmjs.org/<包名>` 的返回码，404 未占用，200 已占用；GitHub 查 `api.github.com/users/<名>` 是否 404，再用 `search/repositories?q=<名>+in:name` 数同名仓库；商标查 USPTO 与 CNIPA，查到记录报注册号与状态，公开渠道查不到就写明查了哪个库、结论是未见记录还是需登录核验。任一项被占，该名淘汰换新，不靠改解释救回，也不许把没查过的候选域名当成查过的交付。交付写清查了哪些域名、各自状态与来源（rdap、whois、doh-ns）、查询时间。可注册不等于能注册成功，保留词和溢价词还得去注册商页面按高价确认。

这条链上没有一步依赖模型品味。任何 agent 拿到 `prompt.txt` 都能照着重跑，结果对不上时，知道该翻哪一段。
